# Deployments

The user opens `Deployments` because this is where planning turns into something people can actually visit.

This desk should feel like a release room, not like a pile of remote controls. The user should not need to understand buckets, collections, or target wiring to ship content. They should choose what they want to release, see what that release includes, and start it with confidence.

The first thing the screen should show is the release shape. Which pages are part of this release? Which content collections will go with it? Which media assets need to travel? Which public address will people use afterward? The user should not be forced to assemble that picture mentally from separate panels.

Before the user presses the main button, the desk should answer the questions they actually care about. Is everything ready? What changed since the last release? How many pages will be updated? Is the media library already in sync or still behind? Will posts and taxonomies be refreshed too? What public links should the user expect at the end?

The release action itself should be singular and strong. One clear button. One flow. A visible list of steps. A user should be able to watch the process move from local preparation to remote updates to final public checks without feeling lost. When something fails, the failure should be described in everyday terms, with the broken step clearly named.

This desk should also respect time. If the user only needs to rerun the same bundle, that should be easy. If the user wants to inspect the history of past releases, that should be available without leaving the desk. They should be able to answer, What went live last time? and Did this release actually finish? in seconds.

The end of the story matters more than the beginning. When a deployment finishes, the user should be rewarded with real browse links. Open the post. Open the category page. Open the media file. See what is live. The system should not celebrate completion while still hiding the output.

The best version of this desk makes the user feel that release is a controlled, understandable ritual. Not magic. Not chaos. Not scattered maintenance. A release.

What would make the user happy:
- The desk explains what will be released before release begins.
- One main action drives the whole flow.
- Each step is visible and understandable.
- Past runs are easy to inspect.
- Browse links appear immediately when the release finishes.

What would make the user angry:
- A release desk full of small unrelated controls.
- Having to guess what changed or what is included.
- A run that fails without naming the broken step.
- A success message with no real link to inspect.
- The sense that deployment is something only the builder of the system can understand.
