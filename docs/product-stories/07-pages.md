# Pages

The user opens `Pages` because they want to decide what gets published, how it is shaped, and where it will appear.

This desk should begin with a simple question: what kind of page are you making? A post page, a category page, or a standalone page. The screen should become smarter from that answer. If the user chooses a post page, the desk should stop talking about unrelated page types. If they choose a category page, the desk should immediately frame the work around categories and their public paths.

The page story should feel like a bridge between content and presentation. The user picks the kind of page, chooses the layout, sets the public pattern, checks the search and social details, and previews the result with a real example. They should feel that the page is a publishing promise, not an abstract document.

For pages that multiply, the desk must make that multiplication visible. If the user creates a post page, they should see how many post pages will be generated. If they create a category page, they should see how many category pages will come out of it. A preview selector should let them inspect a real post or a real category before publishing, so there is no mystery about what the generated page will actually look like.

This desk should also explain output clearly. What is the public path? What is the local path? Which sample pages are already live? Which ones are stale and need a new release? Which ones are still missing? A page desk that cannot answer those questions forces users to guess about the very thing the page exists to do.

Layout work should feel close, not detached. If the user needs to adjust the structure, they should jump to the layout builder and come back without losing the page. If they need to inspect a real output, the desk should offer that link directly. If the page depends on a post or a category, the user should be able to open that source material just as easily.

The SEO part of the story should be useful, not ceremonial. The user should understand what title, description, social image, and canonical address will be used. If the page inherits a sensible default, the screen should say so. If the page overrides it, that should be clear too.

When this desk is right, the user feels that pages are understandable. They know what kind of public surface they are creating, how many outputs it will produce, and what those outputs look like before anyone sees them.

What would make the user happy:
- The desk starts from page type, not implementation details.
- Previewing a real post or category is easy.
- The number of generated pages is visible.
- Live, stale, and missing output states are obvious.
- Layout, source content, and public links are all within reach.

What would make the user angry:
- A page desk that expects the user to think like a system designer.
- No clear distinction between one page and a page template that multiplies.
- No sample output before publishing.
- Public paths that feel opaque.
- Having to leave the desk just to understand whether the page is actually live.
